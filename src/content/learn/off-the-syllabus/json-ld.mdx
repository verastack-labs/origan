Think of a visiting card. You can read it: a name, a phone number, a shop, an area. A person finds it easy. But a machine looking at a photo of the card sees a pile of marks.

Now think of the form a bank gives you, with boxes marked **Name**, **Phone**, **Address**. Nothing is guessed. Each fact sits in a labelled box.

A web page is the visiting card. A search engine, or any other program that reads pages, has to guess which words are the title, which is the date and who wrote it. **[JSON-LD](https://www.w3.org/TR/json-ld11/)** is the labelled form hidden behind the page, so the guessing is not needed.

Let's read it from the outside in.

The `<script>` tag is how a page carries code. This one is special. Its `type` is `application/ld+json`, which is not JavaScript. [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script) says that when a script's type is not JavaScript, its content is treated as a data block and the browser does not process it. So the text sits there, quietly, for anything that wants to read it. Visitors never see it.

The part inside is **JSON**, which stands for JavaScript Object Notation, a plain-text way to write data as names and values. JSON is stricter than JavaScript. Names must be in double quotes, and there are no comments and no trailing commas.

The **LD** stands for **Linked Data**. The W3C, the body that writes web standards, defines JSON-LD 1.1 as a JSON-based format to serialise (write out) Linked Data. In plain words: JSON where the names are linked to agreed meanings.

**Remember:** JSON-LD is ordinary JSON in a script tag whose type tells the browser to leave it alone.

## Three keywords worth knowing

Three names in that block start with an `@`. They are the grammar.

- **`@context`** says which dictionary the words come from. Here it is `https://schema.org`. A context maps short names such as `headline` to full identifiers, so everyone means the same thing by them.
- **`@type`** says what kind of thing the block describes. Here it is [`TechArticle`](https://schema.org/TechArticle).
- **`@id`** gives a thing a name that other parts can point to. The block above does not need one. You will see why in a moment.

The dictionary is **[schema.org](https://schema.org/docs/gs.html)**, a collection of shared vocabularies that webmasters can use to mark up their pages, so that search engines and other applications understand them better. It lists the types and the names that go with each type.

`TechArticle` is one of those types. schema.org describes it as a technical article, such as a how-to guide or step-by-step instructions, and it is a more specific kind of `Article`.

Real pages describe more than one thing. When they do, a block can hold a list called `@graph`, and the things in it can point at each other with `@id`:

**Remember:** `@context` is the dictionary, `@type` is the kind of thing, and `@id` is a name tag other things can point to.

A few things to notice.

- `@id` is an address with a `#studio` at the end. It does not have to open a page. It is only a stable name for the studio, so other blocks can point at it.
- `sameAs` lists other places that identify the same studio, such as its GitHub page.
- The `address` gives the area and city, not a street. The site's code says why: the area is enough to place the studio.
- schema.org's [`Organization`](https://schema.org/Organization) type has all of these properties: `sameAs`, `founder`, `logo`, `address`, `email` and `telephone`.

Two choices are worth explaining. First, `dateModified` is the "Last checked" date, shown at the top of this page: the day each fact was last compared with its source. Second, the type is `TechArticle`, which is a kind of `Article`. [Google's article guide](https://developers.google.com/search/docs/appearance/structured-data/article) lists `Article`, `NewsArticle` and `BlogPosting` as the types it documents, so it never names `TechArticle`; schema.org does, and defines it as a more specific `Article`. This site chose the more specific type.

**Remember:** a good block says only what the visible page already says. Print it from the same data as the page, so the two cannot drift apart.

## Check your work

Google points to two free tools. The **[Rich Results Test](https://search.google.com/test/rich-results)** is the official Google tool for testing your structured data, and it shows which rich results (special-looking search listings) your page can produce. The **[Schema Markup Validator](https://validator.schema.org/)** at validator.schema.org tests any schema.org markup, and does not run Google-specific checks.

A valid block is a start, not a finish. Google says that correct markup is still no promise that your structured data will show up in search results.

## The honest trade-offs

JSON-LD is useful, and it has real costs.

- **It is invisible, so it can lie.** Nobody sees the block, so nobody notices when it is wrong. [Google's guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) say not to mark up content that is not visible to readers, and not to mark up misleading content. Print the block from the same data as the page, as this site does.
- **It promises nothing.** Google says correct markup is no promise of an appearance in search results. Treat it as a way to be understood, not a way to be ranked.
- **Google documents fewer types than schema.org has.** Google's article page lists only `Article`, `NewsArticle` and `BlogPosting`, and says there are no required properties, only recommended ones such as `headline`, `datePublished`, `dateModified`, `author` and `image`. If your goal is a specific search feature, read Google's page for that feature first.
- **It is one more thing to keep right.** Every field you add is a field that can go stale. A small, true block beats a large one that is half wrong.
- **Generators are not a substitute for reading.** A plugin can write a block for you, but you are still the person who must check that every line of it is true.
