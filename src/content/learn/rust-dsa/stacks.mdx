<Part id="what" heading="Last in, [first] out" sub="Like a pile of plates." />

Think of a pile of plates in the canteen. You put a clean plate on top, and when someone needs one, they take the top plate. Nobody pulls from the middle, because the whole pile would wobble.

That is a **stack**. It is a collection where you can only add to the top and only take from the top. The item you added most recently is the first one you get back. This rule is called **LIFO**, short for "last in, first out".

Reach for a stack whenever the most recent thing is the one you need next, or whenever you need to remember what to come back to. Everyday examples are the undo button in an editor, the back button in a browser, and checking that brackets in code are closed in the right order. Your own program uses one too: the **call stack**, which remembers where each running function should return to.

<Part id="idea" heading="Only the [top] moves" sub="Push on, pop off, peek at." />

<StackDiagram />

A stack has three moves, and all of them work on the top.

- **Push** puts a new value on top.
- **Pop** takes the top value off and gives it to you.
- **Peek** shows you the top value without taking it.

If a stack is empty, there is nothing to pop or peek at. In Rust the honest way to say that is to return `None` instead of crashing, so `pop` and `peek` give back an `Option`.

Because every move happens at one end, each is one step, however many items are in the stack. That is what makes a stack so cheap to use.

**Remember:** a stack only lets you touch the top. That limit is what keeps it simple and quick.

<Part id="build" heading="Wrap a [Vec]" sub="A stack is a Vec with fewer doors." />

A `Vec` already stores items in a row and grows at the end. A stack only needs that end, so the simplest stack is a `Vec` wrapped in a new type that exposes only the stack moves.

<Snippet file="lesson4_stack" name="stack-build" />

Go through it in order.

- `Stack<T>` is **generic**. The `T` is a placeholder for any type, so one definition gives you a stack of numbers, of strings, or of anything else. The type is filled in when you use it, as in `Stack<i32>`.
- The field `items` is private, because there is no `pub` on it. Code outside can't reach in and change the middle, so the stack rule can't be broken from the outside.
- `push` adds to the end of the `Vec`. The end of the `Vec` is the top of the stack.
- `pop` returns `Option<T>`, which is `Some(value)` or `None` when empty. It hands the value over, so the caller now owns it.
- `peek` returns `Option<&T>`, a borrowed look at the top. The stack keeps ownership, and the caller can read the value without taking it.

Try it in the Playground. The block above has a `main` ready.

<Part id="std" heading="Vec is already a [stack]" sub="No wrapper needed in everyday code." />

Rust has no separate stack type, because `Vec` does the job. Its end is the top.

`push` and `pop` are the same names. `last()` is peek: it returns an `Option<&T>`. Wrapping the `Vec`, as we did above, is worth doing when you want the type itself to enforce the rule, so nobody can insert in the middle. For a quick tool inside one function, a plain `Vec` is the usual choice.

<Part id="cost" heading="What each move [costs]" sub="n is the number of items on the stack." />

| Operation | Time | Why |
| --- | --- | --- |
| `push` | O(1) amortised | One write at the end; now and then the `Vec` resizes |
| `pop` | O(1) | Takes the last slot |
| `peek` (`last`) | O(1) | Looks at the last slot |
| `len`, `is_empty` | O(1) | The count is stored |
| Search for a value | O(n) | You can only look from the top downwards |
| Space used | O(n) | One slot per item, plus any spare capacity |

Every move that a stack allows is cheap. The price of that is what you give up: a stack has no quick way to find something in the middle.

In all three, the stack holds *things that are still waiting*: an opener waiting for its closer, a number waiting for its operator, a day waiting for a warmer day. When something arrives that settles the newest waiting item, you pop it.

<Part id="interview" heading="Stacks in the [interview]" sub="What to ask, and what to say." />

A stack is often the answer when a problem has things that nest or things that wait. A few habits help.

- **Spot the signals.** Matching pairs (brackets, tags), undoing the latest step, evaluating expressions, and "the next larger element to the right" all point to a stack.
- **Know the monotonic stack.** Problem 3 is the pattern behind a whole family of questions about the next bigger or smaller value. The surprise is that it is O(n): each item goes in once and comes out once.
- **Decide what an empty pop means.** Is it an error, or just "no answer"? Asking shows care, and in Rust it decides whether you return `Option`, `Result`, or panic.
- **Think about recursion too.** A recursive function uses the call stack. Many recursive solutions can be rewritten with your own stack, which avoids very deep calls. You will use this idea again for tree and graph traversal.
- **Say the cost.** "One pass, each item pushed and popped once, so O(n) time, and O(n) space for the stack in the worst case" is a complete answer.
- **In Rust, say why `Vec`.** Explaining that a `Vec` already gives O(1) push and pop at the end, so a separate stack type isn't needed, is the kind of answer that shows you know the standard library.
