<Part id="what" heading="A list that [branches]" sub="Each node can have two children." />

A **tree** is like a linked list where each node can point to more than one next node. The first node is the **root**. A node below another is its **child**, and the node above is its **parent**. A node with no children is a **leaf**. Any node together with everything below it is a **subtree**, which is a smaller tree in its own right.

In a **binary tree**, each node has at most two children, called the left and the right. A **binary search tree** (BST) adds one rule: for every node, everything in its left subtree is smaller, and everything in its right subtree is larger.

That rule is what makes it useful. Reach for a BST when you want to keep values in sorted order and find them quickly. Trees also describe anything that nests: folders inside folders, the parts of a sentence, or the way a maths expression is built from smaller expressions.

<Part id="idea" heading="Smaller left, [larger] right" sub="Each step leaves half the tree behind." />

<TreeDiagram />

The picture shows a BST with seven values. To search for 40, start at the root, 50. Since 40 is smaller than 50, go left to 30. Since 40 is larger than 30, go right, and there it is. Three nodes visited, and the other four never touched.

Every comparison throws away a whole subtree. If the tree is well spread out, which is called **balanced**, each step cuts the remaining nodes roughly in half. Doubling the number of values adds only one more step. That growth is written O(log n), and it is why searching a million values takes about twenty steps.

The catch is the shape. If you insert already-sorted values one after another (1, 2, 3, 4 and so on), every new value goes to the right of the last, and the tree becomes a list with extra steps. Searching then visits every node, which is O(n). So the speed depends on the **height**, the number of levels from the root down to the lowest leaf.

Trees are a good place to meet **recursion**: a function that solves a problem by calling itself on a smaller piece. A tree is a natural fit, because a tree is a node plus two smaller trees. A recursive function needs a **base case**, an answer that needs no more calls. For trees it is nearly always "an empty tree".

<Part id="build" heading="Build a search [tree]" sub="Insert, search, and walk in order." />

A node owns its two children, the same way a linked list node owns the next node in lesson 3. A child is either missing or present, which is `Option<Box<Node>>` again.

<Snippet file="lesson7_tree" name="bst-build" />

Go through it in order.

- `Node` has a `value` and two optional children. `Bst` holds the root and a count.
- `insert_into` takes `link`, a mutable reference to a slot that is either empty or holds a node. If it is empty (`None`), that is where the value belongs, so it fills the slot. If it holds a node, `value.cmp(&node.value)` compares the two and returns an `Ordering`: `Less`, `Greater` or `Equal`. The function then calls itself on the left or right slot. `Equal` means the value is already there, so nothing is added.
- `contains` follows the same path in a loop instead of recursion. `current` is a shared reference that moves down to `&node.left` or `&node.right`. It never needs to change anything, so it only borrows.

<Note title="Why there is no parent pointer">
Many textbook trees give each node a link to its parent. Here that would be a second owner of every node, which Rust does not allow without extra tools. So the code never goes upwards. It goes down by recursion, and the function calls themselves remember the way back. For most tree problems that is all you need.
</Note>

Now the walks. The values in a BST come out in sorted order if you visit the left subtree, then the node, then the right subtree. That visiting order is called **in-order**.

<Snippet file="lesson7_tree" name="bst-walk" also="bst-build" />

`collect_in_order` is recursive. For a node, it first handles everything on the left, then pushes the node's value, then handles everything on the right. When the link is `None`, the `if let` finds nothing, and that is the base case. `height_of` is the same shape: an empty link has height 0, and any other node is 1 plus the taller of its two sides.

The demo in the Playground builds a tree from seven values that arrive in a good order, which has height 3. It then inserts seven values that arrive already sorted, and that tree has height 7.

One honest limit: deleting a value is the fiddliest part of a BST, so we don't build it here. Also, a very lopsided tree makes the recursion go as deep as the tree is tall, which could overflow the stack, as the long linked list did in lesson 3. Balanced trees avoid this.

<Part id="std" heading="Trees inside [BTreeSet]" sub="Balanced search trees, ready made." />

Rust's standard library has no general-purpose `Tree` type, since trees come in so many shapes. What it does have are sorted collections that are trees inside. `BTreeSet` and `BTreeMap` keep their keys in order and stay balanced, so they never degrade to a list.

<Snippet file="lesson7_tree" name="btree-set" />

The values come back in order without you doing anything, and `first` and `last` give the smallest and largest. Inside, a **B-tree** keeps many values in each node, so the tree is wide and shallow, and that suits how computers read memory. Lesson 9 covers `BTreeMap` and range queries in full.

So when do you write your own tree? When the shape *is* the point: a tree of folders, a parse tree, or a trie (lesson 11). When you only need a sorted collection, use a `BTreeSet` or `BTreeMap`.

<Part id="cost" heading="What each move [costs]" sub="h is the height of the tree." />

| Operation | Time | Why |
| --- | --- | --- |
| Insert into a BST | O(h) | Walk down one path, then fill an empty slot |
| Search a BST | O(h) | Walk down one path, discarding a side each step |
| Smallest or largest | O(h) | Keep going left, or keep going right |
| Visit every value (in-order) | O(n) | Each node is visited once |
| Height | O(n) | Has to look at every node |
| Space used | O(n) | One node per value, plus O(h) recursion |

The height is the key. For a balanced tree, h is about log n, so insert and search are O(log n). For a lopsided tree, h can be n, and they are O(n). A `BTreeSet` stays balanced for you, so its insert and search are always O(log n).

<Part id="interview" heading="Trees in the [interview]" sub="What to ask, and what to say." />

Tree questions are everywhere in coding tests, and almost all of them are recursion in disguise. A few habits help.

- **Start with the base case.** For nearly every tree problem, ask "what is the answer for an empty tree?" first. Then ask how the answer for a node follows from the answers for its two children.
- **Know the traversal names.** In **pre-order** you handle the node, then left, then right. **In-order** is left, node, right, which gives a BST's values in sorted order. **Post-order** is left, right, node. **Level order**, from problem 3, uses a queue.
- **Pass information down.** Problem 2 shows the trick: when a node's answer depends on its ancestors, carry the limits down as extra arguments.
- **Ask about the shape.** Is the tree balanced? Can values repeat? Is it a binary search tree, or just a binary tree? The answers decide which tricks are available.
- **Say the cost in terms of height.** "O(h), which is O(log n) if the tree is balanced and O(n) if it is not" is a complete and honest answer. Mention the recursion's stack use too.
- **In Rust, show you know why the types look as they do.** `Option<Box<Node>>` means "maybe a child, which this node owns". Borrowing with `&node.left` instead of cloning shows that you understand ownership.
