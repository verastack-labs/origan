<Part id="what" heading="Look it up by [name]" sub="A key goes in and its value comes out." />

Think of the contact list on your phone. You type a name and the number appears. You never scroll through every contact from the top, because the phone jumps straight to the right one.

That is a **hash map**. It stores pairs. Each pair is a **key** and a **value**: a student's roll number and their name, or a word and how many times it appears. You give the map a key, and it gives you the matching value back, without looking through every pair.

Other languages call this a dictionary, an object or a map. A **hash set** is the same machine with keys only and no values. It answers one question quickly: "is this thing in here?"

Reach for a hash map when you need to look things up by something other than position, or when you need to count, group or remember things. It is the most useful single structure for solving interview problems, because it turns a slow search through a list into a quick lookup.

<Part id="idea" heading="A number from every [key]" sub="Hashing picks a bucket." />

<HashDiagram />

A hash map keeps its pairs in a row of **buckets**, which are small containers numbered from 0. To decide which bucket a key belongs in, it runs the key through a **hash function**. A hash function turns any key into a number, and the same key always gives the same number. The map reduces that number to a bucket number, and the pair goes there.

To find a key later, the map does the same thing: hash the key, jump straight to that bucket, and look only inside it. It does not touch the other buckets.

Two different keys can land in the same bucket. This is called a **collision**, and it is normal. The picture shows it: keys 3 and 11 both end up in bucket 3. The simple answer, used here, is for each bucket to hold a short list of pairs, and to compare keys inside the bucket to find the right one. This is called **chaining**.

As long as the buckets stay short, lookups are quick. A real hash map watches how full it is and, when the buckets get crowded, grows the row of buckets and moves the pairs to spread them out. That is why the cost is O(1) *on average* and not always. A map where every key collides would be one long list.

**Remember:** a hash map finds things by jumping to one bucket, not by searching the whole collection.

Two things follow from this design. A key must be able to be hashed and compared for equality. And the map does not remember the order you added things, so never rely on the order a hash map gives you back.

<Part id="build" heading="Build a tiny [map]" sub="Eight buckets and a remainder." />

This map goes from `i32` keys to `i32` values. It has eight buckets and never grows, so it only shows the idea.

<Snippet file="lesson6_hash" name="tiny-map" />

Go through it in order.

- `buckets` is a `Vec` of `Vec`s. Each inner `Vec` is a bucket holding `(key, value)` pairs, and `len` counts all the pairs.
- `bucket_of` is the hash. It takes the key's **remainder** after dividing by the number of buckets, so every key lands in a bucket from 0 to 7. `rem_euclid` is used rather than `%` because `-1 % 8` is `-1` in Rust, which is not a valid bucket, while `(-1).rem_euclid(8)` is `7`.
- `insert` looks in the key's bucket. If the key is already there, `std::mem::replace` swaps in the new value and returns the old one. Otherwise it pushes a new pair.
- `get` searches only inside the one bucket for a matching key.
- `remove` finds the pair's position and takes it out with `swap_remove`, which fills the gap with the last pair instead of shifting everything. The order inside a bucket doesn't matter, so that is fine.
- `bucket_sizes` is only here so you can see collisions.

<Part id="std" heading="HashMap and [HashSet]" sub="The entry API does the heavy lifting." />

The standard library's `HashMap` is this idea, finished: it grows when needed, it takes any key type that can be hashed and compared, and it is carefully tested.

<Snippet file="lesson6_hash" name="hash-map-basics" />

`insert` returns the old value if the key was already there. `get` returns an `Option<&V>`, a borrowed look at the value, and `None` if the key is missing. The key you pass to `get` is a reference, and you can look up a `String` key with a `&str`.

Counting is the job you will do most. The first idea is to check whether the key exists, then add or insert. Rust has a better tool, the **entry API**:

<Snippet file="lesson6_hash" name="hash-map-entry" />

`counts.entry(word)` finds the slot for that key, whether or not it has a value yet. `or_insert(0)` fills the slot with 0 if it was empty, and in both cases it returns a mutable reference to the value. The `*` in `*... += 1` writes through that reference. The key is looked up once, not twice, and there is no way to forget a case.

Notice how the example ends. It sorts before printing, because a `HashMap` does not promise any order. If you need keys in order, lesson 9 introduces `BTreeMap`.

The entry API has more forms:

<Snippet file="lesson6_hash" name="hash-map-entry-variants" />

`or_default()` fills in the type's default value, which for a `Vec` is an empty one, so it is perfect for grouping. `and_modify` runs only if the key exists, and `or_insert` covers the case where it doesn't.

A `HashSet` is a map with only keys.

<Snippet file="lesson6_hash" name="hash-set" />

`insert` returns `true` if the value was new and `false` if it was already there, which makes de-duplicating and "have I seen this?" checks very short. Sets also have operations like `intersection`, `union` and `difference`.

Finally, your own types can be keys if they can be hashed and compared:

<Snippet file="lesson6_hash" name="hash-derive" />

`#[derive(Hash, PartialEq, Eq)]` asks the compiler to write the code for you. A rule to keep: if two keys are equal, they must hash to the same number, and the derive guarantees that. By default, Rust's hash function is chosen to be hard to attack with keys picked to collide. It is a little slower than the simplest hash functions, and that is a good trade for most programs.

<Part id="cost" heading="What each move [costs]" sub="n is the number of pairs in the map." />

| Operation | Time | Why |
| --- | --- | --- |
| `insert` | O(1) average | Hash, go to one bucket, add or replace |
| `get`, `contains_key` | O(1) average | Hash, search one short bucket |
| `remove` | O(1) average | Same as `get`, then take out |
| `entry(...).or_insert(...)` | O(1) average | One lookup |
| Worst case for any of these | O(n) | Every key collides into one bucket |
| Loop over everything | O(n) | Visit every pair, in no useful order |
| Space used | O(n) | The pairs, plus some spare buckets |

"Average" means that over many operations on ordinary keys, each one takes a constant number of steps, even though one unlucky case could take longer. In practice, a `HashMap` is the way to turn an O(n) search into an O(1) lookup, at the cost of extra memory. Compare it with a `Vec`, where `contains` has to look at every item.

<Part id="interview" heading="Hash maps in the [interview]" sub="The helper that appears everywhere." />

If you only get good at one structure for interviews, make it this one. A few habits help.

- **Ask "can I remember something?"** When a first idea compares every item with every other, try a map or a set that remembers what has been seen. This turns O(n squared) into O(n), and it is the idea behind all three problems here.
- **Know the patterns.** Counting how often things appear (the entry API), looking up a partner or complement (problem 1), grouping by a shared key (problem 2), and checking for membership (problem 3) cover a large share of questions.
- **Ask about duplicates and the key type.** Can values repeat? Are the keys small numbers, where a plain array might do, or strings? Do you need the answer in order?
- **Be honest about "O(1)".** Say "O(1) on average". A strong answer adds that the worst case is O(n) if many keys collide, and that the map uses extra space to buy the speed.
- **Remember that order is not kept.** A `HashMap` returns items in no useful order. If you need sorted keys, say you would use a `BTreeMap` instead.
- **In Rust, use the entry API.** Writing `*counts.entry(x).or_insert(0) += 1` rather than checking and inserting separately shows you know the idiom, and it does one lookup instead of two.
